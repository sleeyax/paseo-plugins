# Working on this plugin

Run `paseo plugin reload guided-review` after every change, then `paseo plugin logs guided-review`.
The reload is the only compile check of the two bundles the daemon builds.
Do this yourself; never leave it to the user.
Where a reload is not wanted, the daemon's own compiler answers the same question: import `compilePlugin` from `@getpaseo/server/dist/server/server/plugins/compiler.js` (inside the CLI's `node_modules`) and run it over the two entries.

## The shape later work builds on

`server/review-service.ts` is the top level: every RPC in `shared/contracts.ts` is one of its methods, and `index.server.ts` does nothing but wire them.
The service keeps what an RPC decides (which review, which forge, whether the guide agent can take a prompt, which verdicts are on offer, the branch flow and "Suggest wording" jobs) and hands the larger work to the modules it composes, each built over the same store and ports:

- `server/review-preparation.ts`, `ReviewPreparation`: the start and Regenerate job, reading the change request and giving the review its workspace (fast-forwarding a branch, reusing or creating a PR workspace, cloning), then recording it.
- `server/guide-generation.ts`, `GuideGenerations`: generating a guide per head as a background job, picking one up after a restart, carrying marks over, archiving the agents of guides that end, and `shown`, the guide the panel shows.
- `server/review-drafts.ts`, `ReviewDrafts`: drafts, their links to nodes or the overview, GitHub's general-comment paragraphs and the review body, and a submit's or discard's effect on them.
- `server/review-inbox.ts`, `ReviewInbox`: the start screen's review list, every forge's `listReviewRequests` joined with the reviews in the store and the check-offs.
- `server/one-at-a-time.ts`, `oneAtATimePer`: the per-key queue that writes of marks, drafts and the body, and GitHub's pending review, go through.

It reaches the outside only through its ports, so its tests replace every one of them:

- `server/forge/port.ts` is the Forge port. `server/forge/github.ts` implements it over `gh` and `server/forge/gitlab.ts` over `glab`, both through `server/forge/cli.ts`, which turns a failed call into a `ForgeError` whose message is shown as it is, and both take their read caps, clone timeout and ghost author from `server/forge/common.ts`.
- `server/workspaces/port.ts` is the workspace port. `server/workspaces/paseo.ts` implements it over the SDK, and `server/workspaces/checkout.ts`, the local checkout module, does the git behind `inspect` and `fastForward`.
- `server/command-runner.ts` is the one seam every `gh`, `glab` and `git` call goes through, and `server/fake-command-runner.ts` replays recorded output through it.
- `server/guide-agent/port.ts` is the guide agent port, which moves text only: `create` starts the agent on a prompt, `reply` waits for its answer, `run` and `send` prompt it again (for "Suggest wording", "Ask about this" and "Ask agent"), `status` says whether it is idle. `server/guide-agent/paseo.ts` implements it over the SDK. Structured output is `server/guide-agent/structured.ts`: `withOutputSchema` puts the JSON Schema in the prompt, `parseReply` finds the JSON in the reply and validates it with zod, and `runStructured` does both for a `{ body }`-style request. `server/guide-output.ts` adds the guide's own checks, which is where layering and coverage go.

A new forge operation goes on the port first, then on each adapter; a new RPC goes in `shared/contracts.ts` and becomes a service method.
The fakes (`server/fake-*.ts`) sit beside the modules rather than in tests so every test shares them, and nothing in `index.server.ts` imports them, so they never reach the bundle.
On the client, `client/theme.ts` holds Paseo's design scale and the one `Colors` type, and `client/button.tsx` the one `Button` (`primary` for the step's main action, `small` among small text).

## Constraints that are not obvious

A Command Center item cannot take text, so starting from a URL is the `start` screen, which the sidebar header item opens.
A screen is not handed the client context, so `createStartScreen` takes the panel opener through its closure, and `client/open-panel.ts` retries it: `client.openPanel` throws until the app's cache has the workspace, which a just-created one reaches a moment later.
The panel takes it the same way, so a move to another workspace (Regenerate's, "Open the PR workspace") opens the panel there rather than just the workspace.
`client.openPanel` always navigates to the workspace, so a tab cannot be added in the background, and Paseo restores a workspace with the tabs it last had and offers plugins no hook when one opens. A review started with Review, which does not navigate, therefore has no panel tab until the reviewer opens it, so `client/review-buttons.ts` keeps a header button that opens the panel on every workspace `getReviewWorkspaces` lists, polling it for reviews started since.

Paseo cuts every plugin RPC off after 30 seconds and does not stop the handler.
Reading a PR, cloning and `workspaces.create` can all take longer, so `start` returns a review ID at once and the work runs as a background job, which the panel follows through `startProgress` and the review list through `getLocalReviews`.
Starts run side by side, but `ReviewPreparation` cuts workspaces one repository at a time (`#perRepository`), since two starts of an uncloned repository would otherwise clone over each other.
A job reads as ready only once `GuideGenerations.state` has been asked, so whatever follows it never sees a ready review with no guide and stops following too early.
`paseo` only arrives on a handler's context; it is one connection for the whole process, so `index.server.ts` keeps the first one for the jobs that outlive their RPC.

A `change_request` workspace is a worktree of an existing clone, and the daemon fetches the PR from that clone's `origin`.
So the clone is found by asking each git project for `git remote get-url origin` (a project carries no remote), and when none matches the repository is cloned with `gh repo clone` or `glab repo clone` into the data directory, which then becomes a Paseo project of its own the first time a workspace is cut from it.

Paseo passes an output schema only with a new agent's first prompt, and only Codex and OpenCode enforce it, so every structured request carries the schema in its prompt and the reply is parsed here, whatever the provider.
There is no generic read-only flag either: `readOnlyMode` picks Claude's `plan` or Codex's `read-only` (valid though unadvertised), and the `agent.permission_requested` hook denies a guide agent's edits, writes, commands and mode changes, recognising it by its `guided-review.review` label because the hook's agent carries no labels and an in-memory list would not survive a reload.
Hooks are best-effort, so `reply` answers whatever is pending itself when `waitForFinish` comes back with `status: "permission"`: in plan mode Claude tends to end by asking to leave it, which is denied with a request to answer as a normal message.
`answerPermission` in `server/guide-agent/paseo.ts` is the one policy: the hook denies only what changes something and leaves the rest to the reviewer, while `reply`, which nobody watches (generation and "Suggest wording"), also allows `read` and `search` tool requests and denies the rest, so an unattended run cannot stall on a prompt.
Sending to a busy agent interrupts its turn (`PaseoAgentSendOptions` has no `activeTurnBehavior`), so `run` and `send` refuse unless the agent is idle.

The guide is generated as a background job keyed by review and head SHA, and `server/review-store.ts` keeps a record per head SHA from the moment the agent is asked, with its agent ID. A panel read that finds a `generating` record with no job behind it waits on the same agent again, which is how a generation survives a plugin reload. A guide belongs to the workspace it was generated in; a new workspace for the review gets a new guide and agent.

`GuideSchema` in `shared/guide.ts` is what the agent writes; `LayeredGuideSchema` is what the store keeps and the panel shows, and only `layOutGuide` in `server/guide-output.ts` turns one into the other.
A node says why it exists in `why` and what it does in `behaviour`, a fact per entry, because reviewers read the guide instead of the diff; `ReviewStore.getGuide` reads a node stored with a single `explanation` as its `why` with no `behaviour`.
A decision's `alternative` carries a `quote` of the author's words, and `keepQuotedDecisions` in `server/guide-output.ts` sets it to null unless the quote is in the change request's title, description, commits or linked issues, or an added line of the diffs the agent was sent; a guide stored before then has no `alternative` at all, so readers test it rather than compare with null.
It also drops a node's decision left with no alternative, and an overview decision whose quote a node's decision has, which is the only place those rules are enforced: the schema lets a node decision's alternative be null, since nothing is retried and one unquoted decision should not fail a whole guide.
A dependency may point only at a node listed earlier, which `parseGuide` enforces and which is what makes the nodes a DAG without a cycle check; the agent never writes a layer.
Layers are longest-path from the foundations, capped at `MAX_LAYERS`: a deeper chain stays in the last layer, still in the agent's order.

A node names its code in `covers` (`shared/guide.ts`): a path, hunk numbers, or line ranges in the new file (the old one for a removed file). `covers` is the only place a node's files come from; `coveredPaths` derives the file list wherever one is wanted (coverage, the panel's Files list, the nodes a whole-file comment or question falls in). The numbers are the ones `server/guide-prompt.ts` labels each hunk with ("Hunk 2"), from `splitHunks` in `server/diff.ts`, so the prompt and the parser must keep cutting patches the same way.
`server/diff.ts` parses patches into `shared/diff.ts`'s model and `resolveCode` cuts a file down to what a node covers, which `parseGuide` uses to reject references the diff lacks and the `node-diff` RPC to return a subject's hunks, parsed afresh from the snapshot at the guide's head. The RPC takes the same `GuideSubject` as "Ask about this": a node gives its `covers`, a file (a Supporting or Unsorted entry) what no node covers of it, `entryCode` in `server/diff.ts`.
Every line keeps its kind, its old and new numbers, and GitLab's running counters `oldPos`/`newPos` (a `line_code` is `sha1(path)_oldPos_newPos`, and a new file's old counter is 0, as GitLab's parser has it), so a draft can be anchored from the line alone. A partly covered hunk comes back as one entry per unbroken run of lines, with `complete: false` and a header recomputed for the run; its lines still lie inside the forge's hunk, which a GitHub range needs.
`node-diff` also gives each line the syntax tokens of Paseo's own highlighter, `@getpaseo/highlight`, through `DiffHighlighter` in `server/diff-highlight.ts`, which ports Paseo's server `diff-highlighter.ts`: each side of a file is highlighted whole, from the file at the base or head (`WorkspacePort.fileAt`, `git show` in the review's workspace) when its lines are the diff's, else from the text the hunks give. The tokens are made on the server because the package's index pulls every grammar into whatever imports it, so the client never imports it: `syntax-colors` hands it the dark and light palettes of the syntax theme the `syntaxTheme` setting names, and `client/diff-view.tsx` picks one by `isDark(surface0)`, since the host's theme gives plugins no syntax colours and its syntax theme setting is not theirs to read; `syntax-themes` lists the themes for the setting. The dependency is why the manifest has a `build`.

Coverage sorts what no node covers, since several nodes may cover different hunks of one file, and nothing may go unshown: the lockfiles and generated files `server/file-classes.ts` set aside before the prompt was built go to Supporting, and `parseGuide` drops any cover naming one (the agent never saw them, so covers are checked only against the files it was sent, and a node left with none is an error); a file the nodes cover every change of is placed; any other file, whole or with the rest `uncoveredCode` leaves of it (each run of uncovered lines that holds an added or removed line with more than whitespace on it, so the blank lines between a node's ranges place nothing), goes to the agent's Supporting entry for it, else Unsorted. A Supporting or Unsorted entry is still just a path: `entryCode` recomputes its partial diff from the guide's nodes wherever it is wanted (`node-diff`, a whole-file comment subject, whose prompts name the lines its entry holds, and carry-over, which compares what the entry shows), and marks and drafts need nothing more, since marks are by path and drafts anchor on the snapshot. `parseGuide` normalises paths before checking them, and reads a cover of a file whose diff the forge withheld as the whole file, since the agent can only have read its lines in the checkout; nothing is retried.
The panel's Tests and Documentation groups are Supporting's `test` and `docs` entries, split off only where the guide is shown and tallied (`splitSupporting` in `shared/guide.ts`), so the stored guide, marks, carry-over and "Ask about this" still treat them as Supporting entries.

"Ask agent" is the new comment box's other way out: `askQuestion` takes the box's `CommentSubject`, as "Suggest wording" does, with the typed text as the reviewer's question, and sends the prompt from `questionPrompt` in `server/question-prompt.ts` through `#sendToGuideAgent`, which checks `status` before `send` so a busy or gone agent gets its own message rather than the port's error; the panel then closes the box and opens the agent's chat, so a host without `navigation.openAgent` is not offered it.
"Ask about this" is `AskAction` in `client/ask-action.tsx`, the one control every node and entry renders: it opens a question-only `CommentBox` (an `ask` `OpenBox`) whose "Ask agent" sends through `askQuestion`, a node as its node subject and a Supporting or Unsorted entry as its file as a whole. A whole-file `CodeSubjectContext` carries the file's `FilePlacement`, its Supporting category or Unsorted and, for a file some nodes cover part of, the head-side lines its entry holds, as `codeReferencesOf` its `entryCode`, so its question and wording prompts say where the guide put it.
"Guide this branch's PR/MR" starts from a workspace, not a URL: `startBranch` reads the branch and `origin` with git (Paseo's `gitRuntime` is a cache that may be missing, and the client snapshot has no branch at all), asks each forge's `findByBranch`, and hands the one change request found, or the one chosen, to the same job as a URL, with the workspace as `own`.
The command item cannot show anything, so it calls the RPC and opens the panel, which follows the start through `getPanel`'s `none.branch` and polls an empty panel now and then for a start made from outside it.
A workspace the guide is attached to is recorded with its `branch`, which is how a later start, from the URL too, knows to fast-forward it again rather than make a PR workspace; a branch left alone gives the record a `note` the panel shows in one line.
The fast-forward fetches the change request's own ref (`refs/pull/<n>/head`, `refs/merge-requests/<iid>/head`) into `FETCH_HEAD` only, so fork PRs work and no remote-tracking branch moves; untracked files count as dirty, and a branch ahead of the head counts as diverged, since either way the agent would not read the head.

"Understood" marks take the same subjects as "Ask about this". `ReviewStore` keeps them as a `ProgressRecord` under `progress/<head SHA>.json`: node IDs, which mean something only within their guide, and Supporting and Unsorted paths, which mean the same in any guide of the review, so carrying marks to a later head can match nodes by their hunks and entries by path. The record names the guide agent it was made with, and marks made with another agent count for nothing, because a guide generated again at the same head (a retry, a new workspace) overwrites the old one under the same SHA with IDs of its own. `summariseProgress` in `shared/progress.ts` drops marks the guide has no node or entry for and tallies the rest per layer, Supporting, Unsorted and overall. `getProgress` (the service's `readingProgress`) is its own RPC rather than part of `getPanel`, and returns null while a guide is not ready or is being generated again. `setUnderstood` takes a list of subjects, one card's or a whole group's from its heading, and refuses them all when one is not in the guide; it writes one guide's marks at a time, so toggles sent together all land. The client hands its `ProgressControl` down through `ProgressContext`, so `UnderstoodToggle` and `ProgressSummary` need no props threaded through the tree.

Drafts live only on the forge, and every listing reads it. `shared/drafts.ts` holds the forge-neutral `DraftLocation` both directions use: a line as a `LineRef` (the old side for a removed line, the new side for any other, which is how both forges read a comment back), a range of one hunk, a file, or `general`, the change as a whole, which is what a comment on a node or on the overview is. The panel sends a location with the `headSha` of the guide it drew, and a head Regenerate has since moved the review off is refused, since the new head numbers its lines differently; `anchorAt` in `server/anchors.ts` looks the lines up in the snapshot at the review's head and hands the port a `DraftAnchor` whose lines carry kind, numbers and GitLab's counters, so an adapter only translates. A range across hunks is refused there, since GitHub cannot take one, and its ends are put in the diff's order.
On GitHub each draft is a thread on the viewer's pending review, built with GraphQL: `pendingReview` finds the viewer's (github.com's own included) or starts one with no `event` on the snapshot's head, and the adapter runs one create at a time per PR so two saves cannot start two. A draft's ID is its comment's node ID (`PRRC_…`), which update and delete take. A comment carries no side, only its thread does, so `listDrafts` pages through `reviewThreads` and keeps the comments whose review is the pending one, replies to published threads included; an outdated thread reads by its original line. The GitHub draft answers under `fixtures/github/` (`pending-review*`, `start-review`, `drafts-*`) are built by hand from the schema, since recording them would write to a real PR.
What the plugin keeps about drafts is `ReviewStore`'s `drafts.json` (`DraftsRecord`), never posted: where each draft was written from, a `DraftLink` keyed by the draft's ID, and GitHub's general comments. `createDraft` takes `from`, a `CommentOrigin` (`shared/drafts.ts`) of the guide at the head the panel drew: a node (its own comment, or one on code drawn inside it, which `CommentNodeContext` in `client/drafts.tsx` supplies) or the overview, with the `quote` the reviewer highlighted there, if any. The link names that guide's head and agent, as marks do, and `listDrafts` returns `LinkedDraft`s whose `from` is followed to the guide the panel shows: the overview stays the overview, and a node goes through `followNode` in `server/carry-over.ts` (the node covering the same code) when the link was made in an earlier guide, else null. The quote stays with the draft, `earlier` once the guide it was highlighted in is not the one shown. `ReviewStore.getDrafts` still reads links written as a bare `nodeId`. A general comment on GitLab is a draft note with no position (`Forge.takesGeneralDrafts`); GitHub has no draft on the whole PR, so it is a paragraph (`server/review-body.ts`) kept in `drafts.json` until a submit posts it through `Forge.postComment` as a PR comment of its own, an issue comment, before the review goes out with the reviewer's own text alone. Its ID is minted (`paragraph-…`, which `updateDraft`/`deleteDraft` route to `drafts.json` rather than the forge). Each paragraph leaves `drafts.json` as soon as it is posted and the first that fails stops the submit, the review skipped, so trying again posts none twice; a Comment with no own text and no draft on the forge posts the comments and discards the pending review instead, since GitHub turns down an empty Comment review. Every read-modify-write of `drafts.json` goes through `ReviewDrafts`' `#changing`, one at a time per review (`oneAtATimePer` in `server/one-at-a-time.ts`, the queue the marks and `github.ts`'s `oneAtATime` use too); a published submit and a discard clear the record.
`client/drafts.tsx` puts a `DraftsControl` in `DraftsContext` at the panel, so `FileDiffView` reaches it without the guide view passing it on, and only one comment box is open at a time (`OpenBox`, keyed by the place that opened it, since two nodes can draw the same line). `client/comment-box.tsx`'s `CommentBox` is the one box every comment is written and edited in; `NewCommentBox` and `DraftCard` are the only places that open one for a comment, which is where actions like "Suggest wording" go, as `CommentBoxAction`s that return the box's new text; `onAsk`, which sends the text elsewhere instead, only `NewCommentBox` and `AskAction` pass, and `AskAction`'s box has no `onSave`, which makes "Ask agent" its main action. A comment on text the reviewer highlights in the guide is a general draft from the overview or the node whose card holds it: `useHighlight` in `client/text-selection.ts` reads the document's selection, which only the web has, and offers it when it lies wholly inside the card's prose (not its code or drafts), and on a mouse's `pointerup`, for a press that started in the text, opens the box through `useCommentOnRelease`, unfocused (`keepSelection`) so the highlight stays copyable, never over another open box. The box carries the text as `OpenBox.quote` and opens under the paragraph or bullet the highlight ends in, `OpenBox.item`: `useCardText` in `client/guide-view.tsx` gives each card a `CardTextContext` in which `Body` and `Bullet` register their elements by item key and draw `ItemCommentBox` under themselves, whose element is registered too and excluded, so neither a highlight nor a press in the box counts as the card's text, and a box with no item, or the button's, goes to the foot of the card, where `OverviewComments` and `NodeComments` list the drafts and offer a comment on the overview or concept with nothing highlighted. A native `Text` reports nothing about its selection, so the phone app comments on a whole paragraph or bullet on a long press instead (`useCommentOnHold`), and its text is not selectable there, which would take the long press. A hunk's lines take the gesture responder: a row reports the line a press starts on as it bubbles past, the container measures itself at the press and maps later moves to rows by their layout. With a mouse a drag selects at once; on touch it arms after a short hold, and before that it yields to the scroll view.
The review record's `header.headSha` is the head of the guide the panel shows, and nothing moves it on its own. `checkHead` asks the forge's `fetchHead` (one small read: GitHub's `headRefOid`, GitLab's `diff_refs.head_sha`, which is what a new read would key the guide by) and says whether it has `moved`; a forge that cannot be asked reads as not moved, with a `message`. Only a moved head is counted, through `commitsSince`, which looks for the guide's head among the change request's latest 100 commits rather than comparing the two heads, so a force-push or rebase that dropped it reads as `rewritten`; a count that cannot be read is left out, never an error. `describeHeadChange` in `shared/head-change.ts` words it for every place that shows it. That is the one "head moved" signal: the banner reads it through `useHeadCheck` in `client/head-check.tsx`, whose query every part of the panel shares, and a verdict should read it too, from the service's `checkHead` at submit time.
A start whose head has moved keeps the guide the review has when its workspace is still open, is the one asked for, and has a guide there that is not failed: only the title, state and draft flag follow the forge, and no branch is fast-forwarded. `regenerate` is the only way to a new head. It runs the start's job in `regenerate` mode, followed through `startProgress` like a start, and the job, whenever the head moved, brings the workspace along: the reviewer's own branch as before, and a PR workspace's branch (Paseo checks a PR out on a local branch) through the same clean fast-forward; a PR workspace that cannot be moved, dirty or force-pushed, is left for a new one, with a `note`, and the client opens the job's `workspaceId` when it is not the panel's. The guide the new one replaces in the same workspace has its agent archived.
The record keeps the head it moved from as `previousHeadSha`, and a guide generated at the new head, by Regenerate or by a later Try again, takes the marks over through `carryMarks` in `server/carry-over.ts` before it reads as ready: a node whose resolved code (each file's path, status and lines' kinds and text, not hunk or line numbers, which a push above renumbers) equals a node's marked in the guide kept at the old head, and a Supporting or Unsorted entry whose diff, what no node covers of its file, did not change. Code in a diff the forge withheld is never equal. Marks at the old head made in another guide than the one kept there carry nothing, as they count for nothing there.
A change request whose branch carries another's commits is told apart in the start and Regenerate job: `Forge.commitChangeRequests` asks which change requests each commit belongs to (GitLab one call per commit, a few at a time, through `mapAtMost`; GitHub one query of `associatedPullRequests`), beside the workspace's preparation, and `foreignWorkOf` in `server/foreign-work.ts` keeps the open and merged ones from another source branch on the record as `foreign`, at the record's head, so a start that keeps the guide keeps it too. Failing to read it never fails the job. `ownWork` walks the first parents from the head, since a merge brings other work in rather than adding any, to find where the own work starts; it is null when the commit list is cut off at `MAX_COMMITS`, since the history is then incomplete. When `ownWork` finds where the own work starts, the job also asks `Forge.changedPaths` for the files changed from its first parent to the head (GitLab's compare, which can time out; GitHub's, which lists at most 300 files: either cut short is null) as `foreign.ownPaths`, and the guide waits on the reviewer's `chooseScope` (`awaitsScope`, the `choosing-scope` guide state, which spawns no agent) before it is generated. The choice is the record's `scope`, carried to every later head, and `ownWorkOf` applies it only where the head's own work can be told apart. A guide of the own work is still of the change request's own diff, so drafts, anchors and marks need nothing new: `keepOwnWork` in `server/file-classes.ts` sets the files outside `ownPaths` aside like lockfiles, as the `foreign` Supporting category, which the agent's schema does not offer and `splitSupporting` makes a group of its own, and `guidePrompt` leaves the foreign commits out. A guide records its `scope`. Switching it is `rescope`, which keeps the ready guide it replaces at the same head under `replaced/<head SHA>.json`, since `saveGuide` would overwrite it, and `#carryMarksOver` carries from that before the previous head; `again`, a retry, still starts unmarked.

`headsUpNote` in `shared/foreign-work.ts` drafts the comment the banner (`client/foreign-work.tsx`) offers to post through `postHeadsUp`, which `Forge.startDiscussion` makes a resolvable thread on GitLab and an issue comment on GitHub; the reviewer's own change request has no author to ask, so it is refused there.

"Suggest wording" is `suggestWordingAction` on both boxes. The panel sends a `CommentSubject` (`shared/contracts.ts`), `{ kind: "code", location }`, a node's `{ kind: "node", nodeId, quote? }` or the overview's `{ kind: "overview", quote? }`, with whatever is in the box and, as for a draft, the `headSha` of the guide it drew, refusing one Regenerate has moved the review off; `suggestWording` resolves it with `commentSubjectContext` in `server/comment-subject.ts`, whose `codeSubjectContext` gives a code subject (the anchored lines, via `anchorAt`, and every node whose resolved `covers` include one of them, or any part of the file for a file comment) and builds the prompt with `wordingPrompt`. A node subject's context is the node and its code references, an overview subject's the overview as the guide has it, and their prompt sections and rules (`conceptContext`, `overviewContext`, `generalRules`) say it goes on the change as a whole and carry the "About the …: " rule; a highlighted passage (`quoteContext`) is given as what the comment is about, never to be quoted, since it is the guide's wording. The prompt does not replay the chat: the agent already has it. An agent's turn outlasts an RPC, so the request is a background job keyed by a random ID that the box polls through `getSuggestion`, which hands a finished result out once; the service refuses a second request to an agent that has one running, as well as a busy or gone one, and never touches the forge.

Finishing a review is `finish`, `saveReviewBody`, `submit` and `discard`. The verdicts on offer are decided only by `verdictOptions` in `server/submit-rules.ts`, from the record's `viewer` against the header's author and a `checkHead` answer: the reviewer's own change request and a closed or merged one hold Approve and Request changes back, while a moved head and an unreadable one leave them on offer with a `warning`, a moved one with `regenerate` too. `submit` calls `checkHead` again whatever the panel last saw, and refuses, sending nothing, a verdict not on offer then, a `headSha` the review was regenerated away from, or an Approve or Request changes whose warning now is about another head than the `forgeHeadSha` the panel's Finish review read (`warnedOfAnotherHead`). It hands the adapter the head it just read as `approveHeadSha`, null when unreadable. The review body lives in `ReviewStore`'s `review-body.json` until submit, on both forges, written before every submit and cleared once one is `published` or discarded; `ownBody`/`saveOwnBody` are the one pair every body edit goes through. GitHub's pending review has a body, but GitHub refuses to edit it while it is empty (`Could not edit a review with a missing body`), which it is on every review started without one, github.com's own included, so it is never written before submit. `submitReview` answers a `SubmitOutcome` rather than throwing at a failed step: an adapter runs its steps through `SubmitSteps` (`server/forge/submit-steps.ts`), which records any failure as the step's message, and says whether the drafts and body are `published`; the service rates the steps `submitted`, `partial` or `failed`. On GitHub it is one step per general comment and then one for the `submitPullRequestReview` mutation on the pending review, started on the snapshot's head when there is none; a submit and a discard queue behind a draft create in the adapter's `oneAtATime`.
The client's `useRegenerate` in `client/head-check.tsx` is the panel's one Regenerate job, which the banner and Finish review's offer both drive, and `useSetHeadCheck` lets Finish review put its fresher head check in the query the banner reads.

The SDK gives a plugin no data directory. `server/paths.ts` derives one in the Paseo home, per daemon, because the workspace IDs it records mean something only to that daemon.

`server/command-runner.ts` keeps the whole of stdout, decoded once, because a truncated JSON document is worse than none; only a runaway command past 256 MiB is cut off, and that is a failure rather than a truncation.
It takes stdin for `--input -`, which is how GraphQL and JSON bodies are sent: `gh api -F` turns a repository called `123` into a number.
A call that prints a file, `Cli.bytes`, has stdout come back base64-encoded (`stdoutEncoding`), which a UTF-8 decode would corrupt, under a cap of its own (`maxStdoutBytes`), crossing which sets `outputExceeded` and fails as a sentence that names the cap.

The description is `getDescription`, read from the snapshot at the review's head, and the head check carries the forge's own (`fetchHead` reads it in the same small read), which `shownDescription` in `client/shown-description.ts` shows instead once the author has edited it.
`ISSUES_KEY` is a page like Finish review, outside `entryOrder`, which the navigator lists first while the review has foreign work: the banner and, while the guide waits on it, the scope choice, which the guide's own place only points to; the stack has no navigator, so it draws both inline.
`DESCRIPTION_KEY` in `client/guide-entries.ts` is a page no progress marks: first in `entryOrder`, where `startEntry` starts while nothing is marked, and skipped by `nextNotUnderstood`; the navigator lists it, and the overview, while the guide is still being written.
Paseo gives plugins no Markdown renderer, so `client/markdown.ts` reads the description with markdown-it's standalone build (its import says why that build) into blocks of its own, and `client/markdown-view.tsx` draws them.
An image goes through `getDescriptionImage`: `Forge.fetchAttachment` recognises only the forge's own attachment URLs (GitHub's `user-attachments`, a repository's `assets` and `user-images`; GitLab's `/uploads/` in either form it writes) and reads them with `gh api <url>` or GitLab's uploads API, which needs 17.4; any other URL is null and never fetched, so a description cannot send the daemon to a host of its choosing.
`server/image-info.ts` reads the format and size from the image's header, since `gh api` gives no content type and GitLab's is `application/octet-stream`, and refuses what the panel's `Image` cannot draw, SVG among them.

The review list is `getInbox`, listed per host by each forge's `listReviewRequests` (`shared/inbox.ts`), so one host failing comes back as its `error` and leaves the rest listed.
The sidebar row's count (`client/start-sidebar-item.tsx`) is `attentionCount` in `client/inbox-filter.ts`, the default filters with `needsAttention` on, over the list's own `INBOX_QUERY_KEY` query, which the installation's React Query cache shares between the row and the screen. The row asks with `staleTime: Infinity`, so it lists only while nothing is cached and otherwise counts what the screen last listed or a check-off wrote, since every listing runs the forge searches.
GitHub drops a review request once the viewer reviews, so the GitHub adapter runs two searches, `REVIEW_SEARCHES`, the open requests and the open PRs the viewer reviewed and is not asked again on, kept only when a `ReviewRequestedEvent` in their timeline asked the viewer or any team, which together mean what GitLab's reviewer list does; it lists github.com only, as `parsePullRequestUrl` takes no other host. Its pages are 50, since a full page of that query timed out as a 502.
GitHub's search says everything a row shows: `viewerLatestReview.commit` against the head is a push since the review, and a PR that is both requested and reviewed was asked again.
GitLab keeps no record of the commit a review was of, so the GitLab adapter compares the viewer's reviewer record's `updatedAt` with the head commit's date, which needs 19.2; a GitLab older than that is turned down by version. Its listing has no draft count without a call per MR, so `ReviewInbox` counts drafts only for the MRs reviewed here, and on those it takes `submittedHeadSha`, the head a published submit from here recorded, over the dates.
A row's `local` (`LocalReview` in `shared/inbox.ts`, from `ReviewInbox.local`) is what this plugin has of the review: its start or Regenerate while it runs or once it failed, which exists before the review's record does, its guide's state, and its workspace while that is open. `useReviewStarts` in `client/start-review.ts` is the start screen's one starter, which the New review dialog and every row share: it starts any number of reviews and follows each, and every listed review not yet settled (`isSettled` in `client/start-progress.ts`), through `getLocalReviews` by `reviewId` rather than listing again, since a listing runs the forge searches. A row reads what was read there over what the list said, until Refresh drops it. A start is written in as begun at once, so it is followed from then on; only Continue opens the panel once the job is ready, and Review never does.
Check-offs are `inbox-check-offs.json` in the data directory (`server/inbox-check-offs.ts`), by URL, apart from the preferences because the client saves those whole and a check-off would be lost to a save sent around it. Each keeps the head and reviewer state of the row the reviewer ticked, which the client sends, so a push between the listing and the tick still brings it back. `follow` runs inside every `getInbox`: it drops a check-off on a new head or on a state of `RETURNING_STATES` it was not checked off in, takes over any other state so a re-request after the reviewer's own comment still counts, and drops one a host listed without an error and in full no longer has. On the client `useCheckOff` (`client/check-off.ts`) writes a tick into the inbox query at once and keeps the URL `held`, which `visibleItems` lets past the check-off filter alone until a refresh, preference change or search releases it.
The list's filters, sort and columns are `inbox-preferences.json` in the data directory (`server/inbox-preferences.ts`), since a plugin client has no storage but the web's, which is per device, and the settings document needs `daemon.manage`; each field falls back on its own (`shared/inbox-preferences.ts`), and the client saves a change whole without reading the answer back, so a slow answer cannot undo a later change.
The panel's column widths are what is kept per device, in the web's `localStorage`, which the client bundle reaches because the app evaluates it in its own global scope.
`client/column-widths.ts` keeps them per workspace and fits them to the window; `client/column-resize.tsx` draws the handles over DOM pointer events, since a plugin cannot import the host's gesture handler.

## GitLab through `glab`

`glab` sends a token from its environment to any `--hostname` it is given, logged in there or not, so the adapter checks each host with `glab auth status --hostname` (exit 0 means logged in) before its first call there, and `matchUrl` turns down an MR URL on any other host with a `ForgeError` the service shows as the rejection.
Every call passes `--hostname`, because `glab` otherwise picks the host from the git remote of whatever directory the daemon runs in; a host on a port cannot be one, so it is the URL's host without the port.

The adapter addresses a project by its numeric ID, looked up once per path, because some GitLab versions turn down a URL-encoded path on the draft notes endpoints.
`glab api --paginate` prints each page as a JSON array of its own, one after another, so paginated lists are read with `--output ndjson` through `Cli.ndjson`.
GitLab's REST API gives no line counts, so additions and deletions are counted from the diffs; a diff GitLab withheld as too large counts as none.
The change request keeps GitLab's `start_sha` as `startSha` beside the base and head SHAs, because a draft note's position names all three.

Each draft is a draft note, its ID GitLab's number, which `draftNoteId` checks before it goes in a path. Writes go through `send`: the JSON body on stdin with `--header 'Content-Type: application/json'`, because `--input -` alone sends no content type and GitLab then reads a form and drops `position`, and bracketed `-f` fields are refused in JSON bodies. `positionOf` builds the position from the anchor alone and `locationOf` reads one back; a range's `line_range` ends carry `line_code`s from the anchor lines' counters, and its top-level lines are its last line's.
GitLab can store a position other than the one sent, or none, without an error, so `createDraft` compares the answer with what it sent (a range by its ends' line codes) and deletes a draft that does not match.
A `PUT` sets the position to whatever it is given, none included, so `updateDraft` reads the draft and sends its position back; an MR-level draft's position comes back all null, and that is not sent.
A `general` anchor is sent with no position at all, an MR-level draft note. `listDrafts` lists a draft with no file as `general`. A reply drafted on the web to a published thread has no position of its own, so when there is one the MR's discussions are read and it is listed where its thread's first note is (`general` for a thread on the MR as a whole).
A submit is `bulk_publish` with `reviewer_state` (`requested_changes`, else `reviewed`), then `approve` with `approveHeadSha` as `sha`, or none when it is null (409 once the MR moved past it), then the reviewer list read for the viewer's state after every verdict. For Approve and Comment that is the `reviewer-state` step, which only reports: `approved` or `reviewed` confirms an Approve, `reviewed` a Comment, anything else or an unreadable list fails the step, and a viewer who is no reviewer (GitLab keeps no state for one) is a done step with a note in its `message`. For Request changes the check is inside the `request-changes` step, which falls back to `mergeRequestRequestChanges` when the state did not take or cannot be read; that mutation takes the full path and the IID as strings through `glab api graphql -f`, and fails as HTTP 200 with `errors`. GitLab before 19.2 drops `note` as well as `reviewer_state`, so the body goes in `note` only when `GET version` says 19.2 or newer; otherwise, unreadable version included, it is posted after the publish as an MR note (`notes`), never both, and `published` is false until it is, so the service keeps it. Nothing after a failed publish is tried. Discard deletes every draft note, MR-level ones included, one by one, and names the ones left.
The draft answers under `fixtures/gitlab/` (`draft-notes.ndjson`, `discussions.ndjson`) are built by hand from the API docs on !3931's diff refs, and the adapter tests build each create's answer from the position it expects. The submit answers (`version`, `reviewers`, the mutation's) are built inline in `gitlab.test.ts` from the docs, as recording them would publish a real review.

The review list asks `glab auth status --all` for the hosts, which exits 1 when any host fails, so it is read through `Cli.report`, which returns what a call printed whatever its exit code; `parseAuthStatus` takes a host from the line that starts its block, and a host it reports logged in is not checked again.

`glab` runs without `PASEO_AGENT_ID` and `GITLAB_BOT_IDENTITY` (`unsetEnv` on the command runner).
A `glab` wrapper can swap in a bot account's token when it sees either, and a daemon restarted from an agent's terminal inherits `PASEO_AGENT_ID`; the review is the reviewer's own, so it is read and written as them.
